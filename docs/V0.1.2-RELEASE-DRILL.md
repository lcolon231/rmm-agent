# v0.1.2 release evidence and canary drill

This is the operator checklist for
[issue #127](https://github.com/lcolon231/rmm-agent/issues/127). It is a
fail-closed release gate, not a statement that the drill has already run.
Do not create `release-notes/v0.1.2.json`, tag the release, or close #127 until
every retained-evidence item below exists at an immutable URL and its SHA-256
digest has been independently verified.

## Release boundary

- Public v0.1.1 source commit:
  `7cc39f221acc2f717eaa62fe1404865e1a6bb046`.
- Public v0.1.1 used `Base.metadata.create_all`; it has no Alembic revision.
- Its reviewed schema is represented by Alembic baseline `0001`.
- v0.1.2 requires Alembic head `0012`.
- `server/scripts/adopt_v011_schema.py` is the only supported way to associate
  an unversioned public-v0.1.1 database with `0001`. It rejects any table,
  column nullability, primary-key, foreign-key, or index drift.
- Adoption enables a forward upgrade. It does **not** make a v0.1.1 server
  compatible with an `0012` database and it does not add an Alembic downgrade.

## Evidence workspace

Use an access-controlled incident/release-evidence location outside the source
tree. The working directory may contain database counts, hostnames, IP
addresses, audit metadata, and deployment topology. It must not contain
plaintext enrollment tokens, bearer credentials, cookies, passwords, private
keys, request bodies, or unredacted browser/network traces.

Record:

- release candidate commit and workflow run URL;
- operator, UTC start/end times, topology, and tool versions;
- encrypted backup, backup manifest, and their SHA-256 digests;
- v0.1.1 schema-adoption JSON;
- migration current/head output;
- production configuration, HTTPS, health, readiness, and metrics results;
- redacted dashboard page descriptions or screenshots;
- canary agent ID and token ID, but never their credentials;
- audit event IDs for token creation, enrollment failure/success, and
  revocations;
- rollback decision JSON, restore-verification JSON, measured RTO, and stated
  RPO/data-loss boundary;
- final pass/fail decision and unresolved issues.

Publish the final redacted records and encrypted backup manifest to immutable,
retention-controlled storage. A local file, mutable branch URL, `latest` URL,
or expiring unretained CI artifact is not sufficient for the release manifest.

## 1. Establish v0.1.1 recovery point

1. Deploy or restore the exact v0.1.1 database and components in a disposable
   production-like environment.
2. Stop enrollment and other database writers.
3. Run `deploy/backup/nodelink-backup.sh` with
   `NODELINK_BACKUP_PASSPHRASE_FILE` pointing to a restricted file. Never put
   the passphrase in an argument or environment value.
4. Copy the encrypted backup and manifest to immutable storage.
5. Restore into a fresh isolated database with
   `deploy/backup/nodelink-restore.sh`.
6. Verify expected row counts and audit state appropriate to v0.1.1. The
   current `verify_restore.py` requires an Alembic revision and current model,
   so run it after the guarded adoption and forward migration described below.

## 2. Guarded schema adoption and upgrade

Use an async SQLAlchemy URL. Keep database passwords in the deployment secret
mechanism; do not paste URLs containing credentials into retained transcripts.

```bash
cd server
python scripts/adopt_v011_schema.py \
  --database-url-env NODELINK_V011_DATABASE_URL \
  --evidence-output ../evidence/v011-schema-check.json
```

The dry run must report an exact match. Any mismatch blocks the release and
must be investigated; do not use `alembic stamp` directly and do not edit the
fingerprint to fit an unexplained database.

After reviewing the dry-run record:

```bash
python scripts/adopt_v011_schema.py \
  --database-url-env NODELINK_V011_DATABASE_URL \
  --stamp \
  --evidence-output ../evidence/v011-schema-adoption.json
ALEMBIC_DATABASE_URL="$NODELINK_V011_DATABASE_URL" python -m alembic upgrade head
ALEMBIC_DATABASE_URL="$NODELINK_V011_DATABASE_URL" python -m alembic current
```

The final revision must be exactly `0012`. Run `verify_restore.py` with the
pre-upgrade minimum counts and `--expected-schema-revision 0012`; retain its
JSON output. The CI PostgreSQL test
`test_public_v011_postgresql_schema_adopts_and_upgrades_to_head` exercises the
same adoption, migration, row-preservation, and cleanup path.

## 3. Production HTTPS deployment

Deploy in the documented order: database, FastAPI, dashboard, then agent.
Use the repository Caddy topology or the deployment's equivalent TLS
terminator. Production validation must have:

- `ENVIRONMENT=production`;
- `DEBUG=false`;
- PostgreSQL `DATABASE_URL`;
- a strong deployment-only `SECRET_KEY`;
- protected command signing key/keyring;
- an HTTPS `PUBLIC_BASE_URL`;
- a server-only dashboard `NODELINK_API_BASE_URL`;
- trusted-proxy settings matching the real proxy boundary.

From outside the proxy boundary, record status and a redacted response summary
for:

```text
GET https://<deployment>/healthz
GET https://<deployment>/readyz
GET https://<deployment>/metrics
GET https://<deployment>/login
```

Do not use `curl -k` or disable agent TLS verification. Verify the certificate
chain and hostname. Confirm proxy, application, analytics, and error-reporting
logs exclude request bodies and sensitive headers.

## 4. Windows canary

Use a disposable Windows endpoint and a fresh temporary directory. Verify the
candidate binary/installer checksum and provenance before execution. Until
[#24](https://github.com/lcolon231/rmm-agent/issues/24) is resolved, record that
the agent and installer are not Authenticode signed.

As an administrator, create a token with:

- a descriptive canary name;
- the disposable site/environment;
- the intended canary hostname and agent-name restrictions;
- expiration no later than 24 hours;
- maximum uses `1`.

Confirm the UI displays plaintext exactly once. Transfer it through an
approved secret channel. Do not paste it into a shell command, command history,
screenshot, ticket, log, or evidence record.

On the endpoint, use hidden interactive entry:

```powershell
.\rmm-agent-windows-amd64.exe enroll `
  --server "https://<deployment>" `
  --name "v012-windows-canary" `
  --config ".\canary\config.json"
```

Then start the foreground process or installed service. Record only the agent
ID, credential fingerprint, service state, and timestamps. Verify:

1. the dashboard reports the agent online after a heartbeat;
2. enrollment-success and token-use audit events reference the expected IDs;
3. success/failure/token metrics changed by the expected bounded amount;
4. reuse of the same token returns the generic enrollment rejection;
5. the failed attempt creates a secret-free audit event;
6. token metadata is used and masked;
7. revoking the token succeeds and is audited;
8. revoking the agent invalidates subsequent authenticated requests and is
   audited;
9. logs and retained artifacts contain neither the token nor agent credential.

Do not attempt token reuse by recovering it from history or storage. Keep the
secret only in the approved transfer mechanism long enough to perform the
negative check, then destroy it.

## 5. Rollback decision and recovery rehearsal

Pause server promotion and external agent rollout first. Preserve an encrypted
backup of the failed `0012` state. Run
`server/scripts/plan_release_rollback.py` with immutable component identifiers,
the live and target schema revisions, `--agent-rollout-paused`, and an evidence
output path.

Public v0.1.1 is not a server/database rollback target for an `0012` database.
If no previously retained production-intended release has a matching verified
backup, the decision must be **forward fix**. A restore rehearsal may still
restore the pre-upgrade v0.1.1 recovery point in isolation to demonstrate RPO
and RTO, but the production decision record must not claim an in-place
downgrade.

Measure:

- RTO from declared rollback start until all verification gates pass;
- RPO from the chosen backup timestamp to the incident cutoff;
- the exact writes intentionally discarded in the isolated restore test;
- restore counts, audit-chain/anchor result, and credential/token
  reconciliation actions.

## 6. Final gate

Run and retain the exact candidate-commit results:

```bash
cd server && pytest -q
cd ../agent && go test ./...
cd ../dashboard
npm ci
npm audit --omit=dev
npm run lint
npm run typecheck
npm test
npm run build
npm run smoke:production
```

Also retain the Windows service/DPAPI/installer lifecycle job, PostgreSQL
backup/restore suite, concurrent single-use enrollment test, HTTPS smoke, and
release artifact checksum/provenance verification.

Only after all records have immutable URLs and verified SHA-256 digests:

1. create `release-notes/v0.1.2.json`;
2. list #24, #66, #84, #125 and any failed/waived gate explicitly;
3. run `validate_release_notes.py --phase preflight`;
4. review the manifest and evidence with a second operator;
5. tag only if the final decision is pass.
